# 스케줄·근태 설계 1~10단계 최종안

이 문서는 화면 설계 직전까지의 스케줄·근태 설계를 현재 확정 기준으로 다시 정리한 문서다.

핵심 원칙은 다음과 같다.

- 스케줄은 예정, 근태는 실제 결과다.
- 테이블에 존재하는 원자 사실만 DTO에 둔다.
- RequestVO는 외부가 결정하는 입력만 받는다.
- ResponseVO는 화면/API가 실제로 필요한 값만 반환한다.
- DB 행동은 DAO/Mapper, 업무 판단은 Service, HTTP 연결은 Controller가 담당한다.
- 스케줄과 근태는 삭제하지 않고 허용된 범위에서 정정한다.
- 근태가 발생한 스케줄은 당시 예정 사실이므로 더 이상 수정하지 않는다.
- 날짜 범위와 계약 기간은 시작 포함·끝 미포함인 `[start, end)`로 통일한다.
- 계약서에 적힌 휴게시간과 실제 근태의 휴게시간은 이름과 의미를 분리한다.
- 야간·연장시간은 `double`을 유지하되 계산 중간값은 분 단위 정수로 다룬다.
- `attendanceStatus`, `breakStart`, `breakEnd`, `휴게중`은 현재 확정 스키마/VO에 없는 개념이므로 사용하지 않는다.

## 현재 패치 상태

| 항목 | 최종 결정 | 실제 연결 상태 |
|---|---|---|
| 스케줄 정정 | 근태 발생 전 employeeNo, scheduleDate, scheduleDayType 모두 정정 가능 | 반영 |
| 스케줄 삭제 | 삭제 기능 없음 | 반영 |
| 관리자/본인 권한 | Controller는 인증정보만 전달하고 Service가 판단 | 실제 연결은 추후 작업 |
| 토큰에서 직원번호 확보 | 직원 계정일 때 TokenParseResponseVO.noType을 직원번호로 사용 | 실제 연결은 추후 작업 |
| 계약 적용기간 | contractStart <= workDate < contractEnd | 반영 |
| 미래 근태 생성 | 과거·오늘만 허용, 미래는 금지 | 규칙 확정, 실제 메서드 연결은 추후 작업 |
| 계약 휴게 컬럼 | written_break_minutes / writtenBreakMinutes | 반영 기준 확정 |
| 시간값 | nightHours, overtimeHours는 double | 반영 |
| Controller | /api 경로, @Valid, @CurrentUser 형식, DELETE 없음 | 반영 |

# 1단계. 현실의 근태 업무 정의

## 1-1. 스케줄과 근태의 역할

~~~text
employee_work_schedule
= 특정 직원이 특정 날짜에 근무일인지 휴무일인지 정한 예정

employee_attendance
= 그 예정 아래에서 실제로 발생한 하루 근태 결과
~~~

미래 날짜에는 스케줄을 만들 수 있지만 실제 결과인 attendance는 만들지 않는다.

## 1-2. 정상 출근

~~~text
로그인 직원 확인
→ 오늘 스케줄 조회
→ 스케줄 없으면 출근 불가
→ 현재 열려 있는 다른 근태 존재 여부 확인
→ 오늘 적용 계약 조회
→ 해당 스케줄의 기존 근태 확인
→ scheduleDayType을 workDayType에 보존
→ 정상 근태 생성
~~~

출근 시 주요 값:

~~~text
workScheduleNo = 오늘 스케줄
contractNo = 오늘 적용 계약
workDate = 출근을 시작한 날짜 00:00
clockIn = 서버 현재 시각
clockOut = null
breakMinutes = 0
attendanceType = 정상
workDayType = scheduleDayType
nightHours = 0
overtimeHours = 0
~~~

계약서의 `writtenBreakMinutes`는 실제 사용한 휴게시간이 아니므로 출근 시 attendance에 자동 복사하지 않는다.

스케줄이 휴무일이어도 출근 자체는 가능하다.

~~~text
scheduleDayType = 휴무일
attendanceType = 정상
workDayType = 휴무일
~~~

이는 원래 휴무 예정이었지만 실제 근무했다는 사실이다.

## 1-3. 정상 퇴근

퇴근 대상은 오늘 날짜의 근태가 아니라 **현재 열려 있는 본인 정상 근태**다.

야간근무가 가능하기 때문이다.

~~~text
workDate = 2026-08-31
clockIn = 2026-08-31 22:00
clockOut = 2026-09-01 06:00
~~~

흐름:

~~~text
로그인 직원 확인
→ 현재 열린 정상 근태 조회
→ clockIn 존재 확인
→ clockOut 미존재 확인
→ 서버 현재 시각을 clockOut으로 확정
→ breakMinutes 검증
→ 실제 근무분 계산
→ attendance.contractNo 기준 계약 근로시간 조회
→ overtimeHours 계산
→ nightHours 계산
→ 저장
~~~

~~~text
총 체류분 = clockOut - clockIn
실근무분 = 총 체류분 - attendance.breakMinutes
~~~

현재 스키마에는 `breakStart`, `breakEnd`가 없다. 따라서 존재하지 않는 휴게 시작/종료 API를 만들지 않는다.

## 1-4. 미출근과 결근

~~~text
scheduleDayType = 근무일
attendance 없음
~~~

이면 미출근 상태지만 DB에 `attendanceType = 미출근`을 만들지 않는다.

~~~text
미출근 != 결근
~~~

관리자가 결근을 확정했을 때만 `attendanceType = 결근` 행을 만든다.

## 1-5. 결근·유급휴가·무급휴가

세 결과는 관리자 확정 업무다.

공통 규칙:

- 대상 날짜에 스케줄이 있어야 한다.
- `scheduleDayType = 근무일`이어야 한다.
- 휴무일에는 결근·유급휴가·무급휴가를 만들 수 없다.
- 같은 스케줄에 기존 근태가 있으면 신규 생성하지 않는다.
- 관리자 자신의 근태 정정은 금지한다.
- 미래 날짜에는 만들 수 없다.

비근무 근태 값:

~~~text
clockIn = null
clockOut = null
breakMinutes = 0
nightHours = 0
overtimeHours = 0
attendanceType = 결근 / 유급휴가 / 무급휴가
workDayType = 근무일
~~~

## 1-6. 정정

정상 근태의 `clockIn`, `clockOut`, `breakMinutes`를 바꾸면 실제근무분, 야간, 연장시간을 함께 다시 계산한다.

정상 → 비근무:

~~~text
clockIn = null
clockOut = null
breakMinutes = 0
nightHours = 0
overtimeHours = 0
attendanceType = 결근 / 유급휴가 / 무급휴가
~~~

비근무 → 정상:

~~~text
clockIn 입력
clockOut 입력
breakMinutes 입력
→ 검증
→ 실제근무분 재계산
→ 야간/연장 재계산
→ attendanceType = 정상
~~~

비근무 ↔ 비근무는 `attendanceType`만 바꾼다.

근태의 귀속값은 유지한다.

~~~text
empAttendanceNo
workScheduleNo
contractNo
workDate
workDayType
~~~

## 1-7. 자기 자신의 근태 정정 금지

~~~text
본인 근태 조회 → 가능
본인 출근/퇴근 → 가능
본인 근태 정정 → 불가
타 직원 근태 정정 → 관리자 권한이 있으면 가능
~~~

# 2단계. 테이블 역할 검증

## 2-1. employee_work_schedule

~~~text
work_schedule_no
employee_no
schedule_date
schedule_day_type
~~~

- `scheduleDate`는 TIMESTAMP / LocalDateTime 유지.
- 업무 의미는 날짜 단위이므로 Service에서 00:00으로 정규화한다.
- 같은 직원의 같은 날짜 스케줄은 하나만 허용한다.

~~~text
UNIQUE(employee_no, schedule_date)
~~~

최종 규칙:

~~~text
등록 O
정정 O
삭제 X
~~~

근태가 없으면:

~~~text
employeeNo 수정 O
scheduleDate 수정 O
scheduleDayType 수정 O
~~~

근태가 이미 있으면 세 값 모두 수정 불가다.

## 2-2. employee_attendance

~~~text
emp_attendance_no
work_schedule_no
contract_no
work_date
clock_in
clock_out
break_minutes
attendance_type
work_day_type
night_hours
overtime_hours
~~~

의미:

~~~text
attendance_type
= 정상 / 결근 / 유급휴가 / 무급휴가

work_day_type
= 근태 발생 당시 스케줄의 근무일 / 휴무일

break_minutes
= 해당 근태에서 실제로 사용한 휴게시간(분)
~~~

`attendanceStatus`, `breakStart`, `breakEnd`는 없다.

한 스케줄당 하루 근태는 최대 하나다.

~~~text
UNIQUE(work_schedule_no)
~~~

## 2-3. employment_contract 휴게시간

~~~text
employment_contract.written_break_minutes
ContractDto.writtenBreakMinutes
~~~

~~~text
writtenBreakMinutes
= 계약서상 휴게시간(분)

EmployeeAttendanceDto.breakMinutes
= 실제 근태에서 사용한 휴게시간(분)
~~~

둘은 의미가 다르며 자동 복사 관계가 아니다.

기존 컬럼이 `break_times`라면:

~~~sql
alter table employment_contract
rename column break_times to written_break_minutes;
~~~

## 2-4. 계약 적용기간

~~~text
[contractStart, contractEnd)
contractStart 포함
contractEnd 미포함
~~~

근로조건 변경 시 기존 계약의 `contractEnd`는 새 계약의 `contractStart`와 같은 시각으로 저장한다.

~~~java
originDto.setContractEnd(newContractDto.getContractStart());
originDto.setContractStatus("ended");
~~~

따라서 적용 계약 조회 기준은:

~~~text
contractStart <= workDate < contractEnd
~~~

이다.

# 3단계. 필요한 기능 목록

## 3-1. 스케줄

관리자:

- 직원 스케줄 등록
- 근태 발생 전 스케줄 정정
- 특정 직원·특정일 조회
- 특정 직원·기간 조회
- 오늘 전체 조회
- 특정일 전체 조회

직원:

- 내 오늘 스케줄 조회
- 내 특정일 스케줄 조회
- 내 기간 스케줄 조회

스케줄 삭제 기능은 없다.

## 3-2. 근태

직원:

- 출근
- 퇴근
- 내 오늘 근태 조회
- 내 기간 근태 조회

관리자:

- 결근 확정
- 유급휴가 확정
- 무급휴가 확정
- 정상 근태의 clockIn, clockOut, breakMinutes 정정
- 정상 → 비근무 정정
- 비근무 → 정상 정정
- 비근무 결과끼리 유형 정정
- 특정 직원 기간 조회
- 특정 날짜 전체 조회
- 근태 상세 조회

## 3-3. 공통 업무 판단

- 직원 + 날짜 스케줄 조회
- 스케줄이 참조되는 근태 존재 여부 확인
- 열린 근태 존재 여부 확인
- 특정 시각 적용 서명 계약 조회
- 관리자 자기 근태 수정 금지
- scheduleDayType / attendanceType 허용값 검증
- 날짜 정규화와 기간 검증
- 실근무·야간·연장시간 계산
- 미래 attendance 생성 금지

## 4-2. RequestVO를 만들지 않는 경우

모든 endpoint마다 RequestVO를 만들지는 않는다.

~~~text
출근
→ RequestVO 없음
→ @CurrentUser + 서버시간

퇴근
→ RequestVO 없음
→ @CurrentUser + 현재 열린 근태

내 오늘 조회
→ RequestVO 없음

특정 날짜 전체 근태 조회
→ @RequestParam LocalDateTime workDate

근태 상세 조회
→ @PathVariable long empAttendanceNo

특정 직원·특정일 스케줄 조회
→ employeeNo + scheduleDate RequestParam

내 특정일 스케줄 조회
→ scheduleDate RequestParam
~~~

# 9단계. ServiceImpl

## 9-1. 스케줄 등록

~~~text
scheduleDayType 검증
→ scheduleDate 00:00 정규화
→ employeeNo + scheduleDate 중복 확인
→ sequence 발급
→ DTO 생성
→ INSERT
~~~

## 9-2. 스케줄 정정

~~~text
scheduleDayType 검증
→ 새 scheduleDate 정규화
→ 현재 스케줄 조회
→ 없으면 실패
→ 해당 schedule의 attendance 조회
→ attendance 있으면 정정 불가
→ 새 employeeNo + scheduleDate 중복 조회
→ 다른 schedule이면 실패
→ 변경점 없으면 종료
→ employeeNo / scheduleDate / scheduleDayType UPDATE
~~~

| 상태 | employeeNo | scheduleDate | scheduleDayType |
|---|---:|---:|---:|
| 근태 없음 | 수정 O | 수정 O | 수정 O |
| 근태 있음 | 수정 X | 수정 X | 수정 X |

## 9-3. 스케줄 삭제

~~~text
등록 O
정정 O
삭제 X
~~~

관련 Service / DAO / Mapper / Controller 삭제 기능을 두지 않는다.


## 9-6. 시간 계산

~~~java
long totalMinutes =
        Duration.between(clockIn, clockOut)
                .toMinutes();

long actualMinutes =
        totalMinutes - attendanceDto.getBreakMinutes();

long contractMinutes =
        Math.round(contractDto.getDailyWorkHours() * 60);

long overtimeMinutes =
        Math.max(0, actualMinutes - contractMinutes);

double overtimeHours =
        overtimeMinutes / 60.0;
~~~

야간시간도 분 단위로 계산한 뒤 마지막에 `/ 60.0` 한다.

## 9-7. 휴게분 검증

~~~java
private void validateBreakMinutes(
        LocalDateTime clockIn,
        LocalDateTime clockOut,
        int breakMinutes) {

    if (breakMinutes < 0) {
        throw new GetOutException();
    }

    long totalMinutes =
            Duration.between(clockIn, clockOut)
                    .toMinutes();

    if (breakMinutes > totalMinutes) {
        throw new GetOutException();
    }
}
~~~

## 10-1. 공통 규칙

## 10-4. 기능 → VO → Service → Controller 수직 검증

| 현실 기능 | Request | Response | Service | Controller |
|---|---|---|---|---|
| 스케줄 등록 | EmployeeWorkScheduleAddRequestVO | void | add | POST /api/work-schedule |
| 스케줄 정정 | EmployeeWorkScheduleUpdateRequestVO | void | update | PATCH /api/work-schedule |
| 관리자 직원 기간 스케줄 | EmployeeWorkScheduleSearchRequestVO | EmployeeWorkScheduleResponseVO[] | findByEmployeeAndPeriod | GET /api/work-schedule/employee/period |
| 본인 기간 스케줄 | WorkSchedulePeriodRequestVO | EmployeeWorkScheduleResponseVO[] | findMyPeriod | GET /api/work-schedule/my/period |
| 출근 | 없음 | AttendanceTodayResponseVO | clockIn | POST /api/attendance/clock-in |
| 퇴근 | 없음 | AttendanceTodayResponseVO | clockOut | PATCH /api/attendance/clock-out |
| 결근 확정 | AttendanceAbsentRequestVO | void | recordAbsence | POST /api/attendance/absence |
| 유급휴가 | AttendanceLeaveRequestVO | void | recordPaidLeave | POST /api/attendance/leave/paid |
| 무급휴가 | AttendanceLeaveRequestVO | void | recordUnpaidLeave | POST /api/attendance/leave/unpaid |
| 정상 근태 시간 정정 | AttendanceWorkTimeUpdateRequestVO | void | updateWorkTime | PATCH /api/attendance/work-time |
| 정상 → 비근무 | AttendanceTypeUpdateRequestVO | void | changeToNonWork | PATCH /api/attendance/non-work |
| 비근무 → 정상 | AttendanceRestoreWorkRequestVO | void | changeToWork | PATCH /api/attendance/work |
| 비근무 유형 변경 | AttendanceTypeUpdateRequestVO | void | changeNonWorkType | PATCH /api/attendance/non-work/type |
| 본인 오늘 근태 | 없음 | AttendanceTodayResponseVO | findMyToday | GET /api/attendance/my/today |
| 본인 기간 근태 | AttendancePeriodRequestVO | AttendanceListResponseVO[] | findMyPeriod | GET /api/attendance/my/period |
| 관리자 특정 직원 기간 근태 | EmployeeAttendanceSearchRequestVO | AttendanceListResponseVO[] | findByEmployeeAndPeriod | GET /api/attendance/employee/period |
| 관리자 특정 날짜 전체 근태 | workDate RequestParam | EmployeeAttendanceListResponseVO[] | findByDate | GET /api/attendance/date |
| 관리자 근태 상세 | empAttendanceNo PathVariable | AttendanceDetailResponseVO | findDetail | GET /api/attendance/{empAttendanceNo} |

이 표를 기준으로 3단계에서 정의한 기능이 4단계 VO, 8단계 Service, 10단계 Controller까지 빠짐없이 내려왔는지 확인한다.

# 완료 기준

현재 문서에서 1~10단계의 기능 누락은 다음 기준으로 보완했다.

~~~text
RequestVO 11개
ResponseVO 5개

관리자 근태 조회 추가
- 특정 직원 기간 조회
- 특정 날짜 전체 조회
- 근태 상세 조회

DAO / Mapper 추가
- findWorkingByEmployee
- findScheduleAndAttendanceByEmployeeAndPeriod
- findScheduleAndAttendanceByDate

Service 추가
- findByEmployeeAndPeriod
- findByDate
- findDetail

Controller 추가
- GET /api/attendance/employee/period
- GET /api/attendance/date
- GET /api/attendance/{empAttendanceNo}
~~~

추후 실제 코드 작업으로 남겨 둔 것은 다음 세 가지다.

1. 관리자/본인 권한을 기존 권한·계약 보조 Service에 실제 연결
2. 직원 계정의 `TokenParseResponseVO.noType`을 `employeeNo`로 실제 연결
3. 결근·유급휴가·무급휴가 생성 메서드에 미래 날짜 금지 검증 실제 연결

이 세 작업을 하기 전까지 새 인증 구조, 임시 권한검사, 존재하지 않는 필드나 endpoint를 추가하지 않는다.
