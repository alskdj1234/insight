# 스케줄·근태 설계 1~10단계 최종안

이 문서는 화면 설계 직전까지의 스케줄·근태 설계를 최종 결정 기준으로 다시 정리한 문서다.

핵심 원칙은 다음과 같다.

- 스케줄은 예정, 근태는 실제 결과다.
- 테이블에 존재하는 원자 사실만 DTO와 응답에 사용한다.
- DB 행동은 DAO/Mapper, 업무 판단은 Service, HTTP 연결은 Controller가 담당한다.
- 스케줄과 근태는 삭제하지 않고 허용된 범위에서 정정한다.
- 근태가 발생한 스케줄은 당시 예정 사실이므로 더 이상 수정하지 않는다.
- 날짜 범위와 계약 기간은 시작 포함·끝 미포함인 [start, end)로 통일한다.
- 계약서에 적힌 휴게시간과 실제 근태의 휴게시간은 이름과 의미를 분리한다.
- 야간·연장시간은 0.5시간 표현을 위해 double을 유지하되, 계산 중간값은 분 단위 정수로 다룬다.

## 현재 패치 상태

| 항목 | 최종 결정 | 실제 연결 상태 |
|---|---|---|
| 스케줄 정정 | 근태 발생 전 employeeNo, scheduleDate, scheduleDayType 모두 정정 가능 | 문서와 구현 기준 반영 |
| 관리자/본인 권한 | Controller는 인증정보만 전달하고 Service가 판단 | 2번 실제 연결은 추후 작업 |
| 토큰에서 직원번호 확보 | 직원 계정일 때 TokenParseResponseVO.noType을 직원번호로 사용 | 3번 실제 연결은 추후 작업 |
| 계약 적용기간 | contractStart <= workDate < contractEnd | 반영 |
| 미래 근태 생성 | 과거·오늘만 허용, 미래는 금지 | 방향 확정, 5번 실제 코드 반영은 추후 작업 |
| 계약 휴게 컬럼 | written_break_minutes / writtenBreakMinutes | 전파 기준 반영 |
| 시간값 | nightHours, overtimeHours는 double | 유지 |
| Controller | /api 경로, @Valid, @CurrentUser 형식, DELETE 없음 | 반영 |

# 1단계. 현실의 근태 업무 정의

## 1-1. 스케줄과 근태의 역할

~~~text
employee_work_schedule
= 특정 직원이 특정 날짜에 근무일인지 휴무일인지 정한 예정

employee_attendance
= 그 예정 아래에서 실제로 발생한 하루 근태 결과
~~~

따라서 미래 날짜에는 스케줄을 만들 수 있지만 실제 결과인 근태 행은 만들지 않는다.

## 1-2. 정상 출근

~~~text
로그인 직원 확인
→ 오늘 스케줄 조회
→ 오늘 적용 계약 조회
→ 당일 근태 중복 확인
→ 스케줄의 근무일/휴무일을 workDayType에 복사
→ 정상 근태 생성
~~~

출근 시 저장하는 주요 값:

~~~text
workScheduleNo = 오늘 스케줄
contractNo = 오늘 적용 계약
workDate = 오늘 00:00
clockIn = 현재 시각
clockOut = null
breakMinutes = 0
attendanceType = 정상
workDayType = scheduleDayType
nightHours = 0
overtimeHours = 0
~~~

계약서의 휴게시간은 실제로 사용한 휴게시간이 아니므로 출근 근태에 복사하지 않는다.

## 1-3. 정상 퇴근

~~~text
본인 근태 조회
→ attendanceType = 정상 확인
→ clockIn 존재 확인
→ clockOut 미존재 확인
→ 현재 시각을 clockOut으로 확정
→ 실제 휴게분을 반영해 실근무시간 계산
→ 계약 dailyWorkHours 기준으로 연장시간 계산
→ 야간시간 계산
→ 저장
~~~

~~~text
총 체류분 = clockOut - clockIn
실근무분 = 총 체류분 - attendance.breakMinutes
~~~

현재 스키마에는 실제 휴게 시작·종료 시각이 없다. 따라서 존재하지 않는 시각값이나 별도 휴게 API를 만들지 않는다. 실제 휴게분은 지원되는 정정 요청 또는 기존 입력 흐름으로 저장하며, 자동 계산이 필요해지는 시점에 실제 스키마와 API를 먼저 확정한다.

## 1-4. 결근·유급휴가·무급휴가

이 세 결과는 관리자만 확정한다.

공통 규칙:

- 대상 날짜에 스케줄이 있어야 한다.
- scheduleDayType이 근무일이어야 한다.
- 휴무일에는 결근·유급휴가·무급휴가를 만들 수 없다.
- 실제 정상 근무가 이미 존재하는 경우 단순 신규 생성으로 덮지 않는다.
- 관리자 자신의 근태는 관리자가 직접 정정하지 못한다.
- 미래 날짜에는 만들 수 없다. 이 검증의 실제 코드 연결은 추후 5번 작업에서 반영한다.

비근무 근태의 값:

~~~text
clockIn = null
clockOut = null
breakMinutes = 0
nightHours = 0
overtimeHours = 0
attendanceType = 결근 / 유급휴가 / 무급휴가
workDayType = 근무일
~~~

## 1-5. 정정

정상 근태의 출퇴근·실제 휴게분을 고치면 야간·연장시간을 함께 다시 계산한다.

정상에서 비근무 결과로 바꿀 때는 실제 근무값을 모두 초기화한다. 비근무 결과에서 정상으로 바꿀 때는 clockIn, clockOut, breakMinutes를 입력받아 검증한 뒤 계산값을 다시 만든다.

근태 행과 그 행이 참조하는 스케줄·계약의 귀속은 유지한다. 결과를 고친다는 이유로 이력 자체를 삭제하지 않는다.

# 2단계. 테이블 역할 검증

## 2-1. employee_work_schedule

~~~text
work_schedule_no
employee_no
schedule_date
schedule_day_type
~~~

- scheduleDate는 TIMESTAMP와 LocalDateTime을 유지한다.
- 업무 의미는 날짜 단위이므로 저장과 조회 전에 00:00으로 정규화한다.
- 같은 직원의 같은 날짜 스케줄은 하나만 허용한다.

## 2-2. employee_attendance

~~~text
emp_attendance_no
work_schedule_no
contract_no
work_date
clock_in
clock_out
break_minutes
attendance_type
work_day_type
night_hours
overtime_hours
~~~

이 테이블은 실제 존재하는 값만 가진다.

~~~text
attendance_type
= 정상 / 결근 / 유급휴가 / 무급휴가

work_day_type
= 근태가 발생한 당시 스케줄의 근무일 / 휴무일

break_minutes
= 해당 근태에서 실제로 사용한 휴게시간(분)
~~~

응답도 이 원자값을 기준으로 구성한다. 테이블과 기존 화면 계약에 없는 별도 파생 필드는 추가하지 않는다.

## 2-3. employment_contract

계약서에 적힌 휴게시간은 다음 이름을 사용한다.

~~~text
employment_contract.written_break_minutes
ContractDto.writtenBreakMinutes
~~~

의미:

~~~text
writtenBreakMinutes
= 계약서상 휴게시간(분)

EmployeeAttendanceDto.breakMinutes
= 실제 근태에서 사용한 휴게시간(분)
~~~

둘은 비교 대상이 될 수 있지만 자동 복사 관계가 아니다.

기존 컬럼이 break_times라면 Oracle 변경문은 다음과 같다.

~~~sql
alter table employment_contract
rename column break_times to written_break_minutes;
~~~

## 2-4. 계약 적용기간

계약 기간은 모든 조회에서 다음 의미로 통일한다.

~~~text
[contractStart, contractEnd)

contractStart 포함
contractEnd 미포함
~~~

근로조건 변경 시 기존 계약의 contractEnd를 새 계약의 contractStart와 같은 시각으로 저장한다. 그러므로 경계 시각에는 새 계약만 적용되어야 한다.

# 3단계. 필요한 기능 목록

## 3-1. 스케줄

관리자:

- 직원 스케줄 등록
- 근태 발생 전 스케줄 정정
- 특정 직원·특정일 조회
- 특정 직원·기간 조회
- 오늘 전체 조회
- 특정일 전체 조회

직원:

- 내 오늘 스케줄 조회
- 내 특정일 스케줄 조회
- 내 기간 스케줄 조회

스케줄 삭제 기능은 만들지 않는다.

## 3-2. 근태

직원:

- 출근
- 퇴근
- 내 오늘 근태 조회
- 내 기간 근태 조회

관리자:

- 결근 확정
- 유급휴가 확정
- 무급휴가 확정
- 정상 근태의 clockIn, clockOut, breakMinutes 정정
- 정상 → 비근무 결과 정정
- 비근무 결과 → 정상 정정
- 비근무 결과끼리 유형 정정
- 특정 직원 기간 조회
- 특정 날짜 전체 조회
- 근태 상세 조회

현재 테이블이 지원하지 않는 기능은 목록에 추가하지 않는다.

## 3-3. 공통 업무 판단

- 직원 + 날짜의 스케줄 조회
- 스케줄이 참조되는 근태 존재 여부 확인
- 직원 + 날짜의 근태 중복 확인
- 특정 시각에 적용되는 서명 계약 조회
- 관리자 자기 근태 수정 금지
- scheduleDayType, attendanceType 허용값 검증
- 날짜 정규화와 기간 검증
- 실근무·야간·연장시간 계산
- 미래 근태 생성 금지

# 4단계. RequestVO / ResponseVO

## 4-1. 스케줄 등록

~~~java
@Data
public class EmployeeWorkScheduleAddRequestVO {

    @Positive
    private long employeeNo;

    @NotNull
    private LocalDateTime scheduleDate;

    @NotBlank
    private String scheduleDayType;
}
~~~

Bean Validation은 필수값과 숫자 범위를 확인한다. 근무일·휴무일 같은 업무값 검증은 Service에 둔다.

## 4-2. 스케줄 정정 최종안

~~~java
@Data
public class EmployeeWorkScheduleUpdateRequestVO {

    @Positive
    private long workScheduleNo;

    @Positive
    private long employeeNo;

    @NotNull
    private LocalDateTime scheduleDate;

    @NotBlank
    private String scheduleDayType;
}
~~~

삭제를 제공하지 않으므로 근태 발생 전에는 직원, 날짜, 일 유형을 모두 바로잡을 수 있어야 한다.

## 4-3. 근태 정정 요청

실제 근무정보 정정 요청은 DB에 존재하는 원자값만 받는다.

~~~java
@Data
public class AttendanceWorkTimeUpdateRequestVO {

    @Positive
    private long empAttendanceNo;

    @NotNull
    private LocalDateTime clockIn;

    @NotNull
    private LocalDateTime clockOut;

    @PositiveOrZero
    private int breakMinutes;
}
~~~

비근무 결과를 정상으로 복원하는 요청도 clockIn, clockOut, breakMinutes를 사용한다. nightHours와 overtimeHours는 요청받지 않고 Service가 계산한다.

결근·휴가 요청의 날짜는 @NotNull로 검증하고, 미래 여부는 Service 업무 규칙으로 검증한다.

## 4-4. ResponseVO

스케줄 응답:

~~~java
@Data
public class EmployeeWorkScheduleResponseVO {
    private long workScheduleNo;
    private long employeeNo;
    private LocalDateTime scheduleDate;
    private String scheduleDayType;
}
~~~

근태 응답:

~~~java
@Data
public class AttendanceTodayResponseVO {
    private Long empAttendanceNo;
    private Long workScheduleNo;
    private LocalDateTime workDate;
    private String workDayType;
    private String attendanceType;
    private LocalDateTime clockIn;
    private LocalDateTime clockOut;
    private int breakMinutes;
    private double nightHours;
    private double overtimeHours;
}
~~~

스케줄은 있지만 근태가 없을 수 있으므로 근태 PK는 Long을 사용할 수 있다. 응답에 별도 화면 해석 필드를 추가하지 않고, 실제 스케줄·근태값과 null 여부를 반환한다.

## 4-5. 계약 VO 명칭 전파

계약 등록·수정·조회 VO에서 모두 다음 이름을 사용한다.

~~~java
@PositiveOrZero
private int writtenBreakMinutes;
~~~

0분을 허용하므로 @Positive가 아니라 @PositiveOrZero를 사용한다.

## 5-4. 시간값 자료형

야간·연장시간은 30분을 0.5시간으로 표현하기 위해 double을 유지한다.

~~~text
30분  → 0.5
90분  → 1.5
150분 → 2.5
~~~

부동소수점 오차를 줄이기 위해 계산은 분 단위 long으로 끝낸 뒤 마지막에만 시간으로 바꾼다.

~~~java
long overtimeMinutes = actualMinutes - contractMinutes;
double overtimeHours = overtimeMinutes / 60.0;
~~~

# 7단계. Mapper

## 7-1. 날짜 비교

scheduleDate와 workDate는 TIMESTAMP지만 날짜 단위 업무다. 단건 조회와 중복 확인도 [day, nextDay) 범위로 비교한다.

~~~sql
where employee_no = #{employeeNo}
  and schedule_date >= #{dayStart}
  and schedule_date < #{nextDayStart}
~~~

기간 조회도 동일하게 [startDate, endDate)로 사용한다.

## 7-2. 스케줄 정정

~~~xml
<update id="workScheduleUpdate">
    update employee_work_schedule
    set employee_no = #{employeeNo},
        schedule_date = #{scheduleDate},
        schedule_day_type = #{scheduleDayType}
    where work_schedule_no = #{workScheduleNo}
</update>
~~~

## 7-3. 적용 계약 조회

~~~xml
<select id="findApplicableContract"
        resultType="ContractDto">
    select *
    from employment_contract
    where employee_no = #{employeeNo}
      and signed_time is not null
      and contract_start <![CDATA[ <= ]]> #{workDate}
      and (
          contract_end is null
          or contract_end <![CDATA[ > ]]> #{workDate}
      )
    order by contract_start desc
</select>
~~~

최종 조건은 다음과 같다.

~~~text
contractStart <= workDate < contractEnd
~~~

contractEnd에 >=를 사용하지 않는다. 기존 계약 종료시각과 새 계약 시작시각이 같을 때 두 계약이 동시에 잡히는 것을 막는다.

근로조건 변경 Mapper도 기존 계약에 실제로 다음 값이 저장되는지 확인한다.

~~~sql
contract_end = 새 계약 contract_start
contract_status = 'ended'
~~~

## 7-4. 계약 휴게 컬럼 전파

계약 INSERT, UPDATE, SELECT 전부 다음 이름으로 통일한다.

~~~xml
written_break_minutes
#{writtenBreakMinutes}
~~~

예:

~~~xml
<update id="updateContract">
    update employment_contract
    set written_break_minutes = #{writtenBreakMinutes}
    where contract_no = #{contractNo}
</update>
~~~

findWorkTimeCondition에도 최종 컬럼명을 사용한다.

~~~sql
select daily_work_hours,
       weekly_work_hours,
       written_break_minutes
from employment_contract
where contract_no = #{contractNo}
~~~

반면 employee_attendance는 실제값인 break_minutes / breakMinutes를 그대로 유지한다.

## 7-5. 스케줄과 근태 기간 조회

근태가 없는 근무일과 휴무일까지 조회하려면 스케줄을 기준으로 LEFT JOIN한다.

~~~sql
from employee_work_schedule S
left join employee_attendance A
  on S.work_schedule_no = A.work_schedule_no
where S.employee_no = #{employeeNo}
  and S.schedule_date >= #{startDate}
  and S.schedule_date < #{endDate}
order by S.schedule_date asc
~~~

WHERE에서 A.work_date를 사용하면 근태가 없는 날이 제거되므로 S.schedule_date를 기준으로 한다.

## 7-6. 삭제 SQL

스케줄·근태 Mapper에 delete SQL을 두지 않는다.

# 9단계. ServiceImpl

## 9-1. 스케줄 등록

~~~text
scheduleDayType 업무값 검증
→ scheduleDate를 00:00으로 정규화
→ 직원 + 날짜 중복 확인
→ DTO 생성
→ INSERT
~~~

DB UNIQUE 제약은 마지막 방어선이고, Service에서도 업무 예외로 중복을 막는다.

## 9-2. 스케줄 정정 최종 규칙

근태 발생 전에는 employeeNo, scheduleDate, scheduleDayType을 모두 정정할 수 있다.

~~~java
@Transactional
@Override
public void update(
        EmployeeWorkScheduleUpdateRequestVO requestVO) {

    validateScheduleDayType(requestVO.getScheduleDayType());

    LocalDateTime scheduleDate =
            requestVO.getScheduleDate()
                    .toLocalDate()
                    .atStartOfDay();

    EmployeeWorkScheduleDto currentSchedule =
            employeeWorkScheduleDao.find(
                    requestVO.getWorkScheduleNo());

    if (currentSchedule == null) {
        throw new TargetNotfoundException();
    }

    if (employeeAttendanceDao.findBySchedule(
            currentSchedule.getWorkScheduleNo()) != null) {
        throw new GetOutException();
    }

    EmployeeWorkScheduleDto duplicatedSchedule =
            employeeWorkScheduleDao.findByEmployeeAndDate(
                    requestVO.getEmployeeNo(),
                    scheduleDate);

    if (duplicatedSchedule != null
            && duplicatedSchedule.getWorkScheduleNo()
                    != currentSchedule.getWorkScheduleNo()) {
        throw new GetOutException();
    }

    if (currentSchedule.getEmployeeNo()
                == requestVO.getEmployeeNo()
            && currentSchedule.getScheduleDate()
                .equals(scheduleDate)
            && currentSchedule.getScheduleDayType()
                .equals(requestVO.getScheduleDayType())) {
        return;
    }

    currentSchedule.setEmployeeNo(
            requestVO.getEmployeeNo());
    currentSchedule.setScheduleDate(scheduleDate);
    currentSchedule.setScheduleDayType(
            requestVO.getScheduleDayType());

    if (!employeeWorkScheduleDao.update(currentSchedule)) {
        throw new GetOutException();
    }
}
~~~

중복 조회 결과가 현재 스케줄 자신일 수 있으므로 PK를 비교한다.

| 상태 | employeeNo | scheduleDate | scheduleDayType |
|---|---:|---:|---:|
| 근태 없음 | 수정 O | 수정 O | 수정 O |
| 근태 있음 | 수정 X | 수정 X | 수정 X |

## 9-3. 스케줄 삭제 폐기

~~~text
등록 O
정정 O
삭제 X
~~~

잘못 등록한 스케줄은 근태 발생 전에 update로 바로잡는다. 근태가 발생한 뒤의 스케줄은 역사적 예정 사실이므로 수정·삭제하지 않는다.

## 9-4. 적용 계약 조회

출근, 결근, 휴가 생성 시 대상 직원과 workDate로 findApplicable을 호출한다. Mapper의 기간 규칙은 [contractStart, contractEnd)다.

계약이 없거나 직원이 다르면 근태를 만들지 않는다.

## 9-5. 미래 근태 생성 금지

최종 업무 규칙:


방향은 확정되었지만 이 검증을 실제 메서드들에 연결하는 작업은 사용자가 추후 처리한다. 현재 문서에서는 TODO 경계를 넘어서 임의로 구현 완료로 표시하지 않는다.

## 9-7. 퇴근과 시간 계산

~~~java
long totalMinutes =
        Duration.between(clockIn, clockOut)
                .toMinutes();

long actualMinutes =
        totalMinutes - attendanceDto.getBreakMinutes();

long contractMinutes =
        Math.round(contractDto.getDailyWorkHours() * 60);

        Math.max(0, actualMinutes - contractMinutes);

        overtimeMinutes / 60.0;
~~~

야간시간도 겹치는 구간을 분 단위로 합산한 뒤 마지막에 60.0으로 나눈다.

## 9-8. 실제 휴게분 검증

실제 휴게분은 음수일 수 없고 총 체류분을 초과할 수 없다.

~~~java
private void validateBreakMinutes(
        LocalDateTime clockIn,
        LocalDateTime clockOut,
        int breakMinutes) {

    if (breakMinutes < 0) {
        throw new GetOutException();
    }

    long totalMinutes =
            Duration.between(clockIn, clockOut)
                    .toMinutes();

    if (breakMinutes > totalMinutes) {
        throw new GetOutException();
    }
}
~~~

계약서의 writtenBreakMinutes는 계약 사실이며, 현재 확정되지 않은 비교·강제 규칙을 만들지 않는다.


비근무 근태에서는 모든 실제 근무값을 null 또는 0으로 저장한다.

## 9-10. 근태 정정

# 10단계. Controller

Controller는 다음 일만 한다.

~~~text
HTTP 요청 수신
→ 인증정보 수신
→ RequestVO 검증
→ Service 호출
→ ResponseVO 반환
~~~

권한 판단, 날짜 정규화, 중복 판단, 상태 전이, 시간 계산, DAO 호출은 Controller에 두지 않는다.

## 10-1. 공통 규칙

- 기본 경로는 /api/work-schedule, /api/attendance다.
- 클래스에 @RestController와 @CommonsApiResponse를 사용한다.
- 요청 본문 VO에는 @Valid @RequestBody를 붙인다.
- 인증정보는 @CurrentUser TokenParseResponseVO parseVO로 받는다.
- 삭제 endpoint는 두지 않는다.
- 현재 테이블에 없는 동작을 위한 endpoint를 추가하지 않는다.
- 2·3번 연결을 위해 Service 인터페이스를 임시 방식으로 억지 변경하지 않는다. 기존 시그니처에 맞추고 별도 연결 작업에서 완성한다.

# 완료 기준

이 문서의 1~10단계는 화면/API 역검증 전까지의 최종 기준이다.

추후 실제 코드 작업으로 남겨 둔 것은 다음 세 가지다.

1. 관리자/본인 권한을 기존 권한·계약 보조 Service에 실제 연결
2. 직원 계정의 TokenParseResponseVO.noType을 employeeNo로 실제 연결
3. 결근·유급휴가·무급휴가 생성 메서드에 미래 날짜 금지 검증 실제 연결

이 세 작업을 하기 전까지는 새 인증 구조, 임시 권한검사, 존재하지 않는 필드나 endpoint를 추가하지 않는다.
